## [Unreleased]

### Fixed

- `BleSharedBridge`: Secondary tabs now receive the Primary's `device_information` (`lr`, `range`, etc.) through the heartbeat. Previously it stayed `''` in Secondary tabs, so `device_information.lr` was unavailable and foot-relative `gait.direction` 3/4 could not be mapped to left/right. Mixed versions keep working (an older Primary simply shares nothing).
- `CoreToolkit`: changing the acc range, gyro range or LED brightness no longer overwrites the local `device_information.lr` with `0xFF` (the "keep LR unchanged" value is now set only on the copy that is written to the device).
- `examples/GAME-DDR`: uses the actual `gait.direction` values (1 forward, 2 backward, 3 inside, 4 outside) and the CORE's LR setting to choose lanes. The old 0/2/4/6 mapping sent backward steps to ↑ and outside steps to ↓, and ignored forward/inside steps.
- Use the deployed SDK in GAME-RHYTHM, WORKSHOP_07, drum_test and the FSR visualization example so CORE 3 discovery and 104-byte sensor-packet fixes reach those pages. Initialize callbacks once in GAME-HURDLE-VS, GAME-HURDLE-2D-VS and GAME-HURDLE-VS-advance, leave connection startup to CoreToolkit, and let each player explicitly select a device.
- Discover CORE devices advertising a `CR-` name or the sensor service even when the information-service UUID is absent from the advertisement. Existing information-service discovery and required GATT service permissions remain available.
- Decode header-50 notifications sent as a 104-byte buffer with 12 trailing zero bytes, using the same four-frame payload as the legacy 92-byte format. Reject other lengths and nonzero padding before advancing the serial-gap tracker; raw `gotData` callbacks still receive the original packets.
- Initialize GAME-HURDLE sensor callbacks once and leave connection startup to CoreToolkit. Per-characteristic `onConnect` events no longer count as separate physical devices or start nested `begin()` calls, which attempted to open the second chooser without a user gesture. Both game toggles explicitly open a fresh device choice so old remembered devices or a failed candidate can be replaced.

### Changed

- `examples/GAME-DDR` is now presented as "ORPHE STEP BEAT" (ステップビート): game page title and description, README, landing pages, catalog and gallery, plus a new thumbnail taken from the current screen. The folder name and URL (`examples/GAME-DDR/`) stay the same so existing links keep working; historical notes inside the folder are left as written.
- New example GAME-SUPER-HURDLE ("SUPER VIRTUAL HURDLE"), a remaster of GAME-HURDLE kept as a separate example because its three.js stadium is heavier and has not been checked on older PCs or Android; GAME-HURDLE itself is unchanged. Presentation: night stadium with an animated crowd, LED boards, a live big screen, rival sprinters in the other lanes, the runner's own shadow and first-person limbs, HDR bloom / speed blur, a fully procedural Web Audio soundtrack (adaptive music, crowd, foley) and a broadcast-style HUD, result card and in-page name entry (replacing `prompt()`). The game is split into `main.js` / `world.js` / `runner.js` / `fx.js` / `audio.js` / `ui.js` / `style.css`. The ORPHE CORE initialization script, sensor cooldowns, the existing physics constants, hurdle collision, finish detection and ranking storage are unchanged.
- GAME-SUPER-HURDLE jump rule (new default, switchable): the runner can no longer accelerate while airborne, and speed decays by 12% over the 0.625 s flight (`JUMP_SPEED_LOSS` in `main.js`), so every jump costs ground time. Previously holding the accelerate input in the air accelerated exactly as on the ground.
- GAME-SUPER-HURDLE stamina rule (new default, switchable): stamina is a pacing budget for the 110 m. It burns with the square of how far the runner is above a cruise speed (8.4 m/s), recovers slowly at or below it, and running dry halves top speed until stamina is back to 35%. An even pace that empties the tank on the line is fastest; flat out all the way runs dry at about 80 m. The HUD shows a `PACE` marker and how far ahead of / behind that pace the runner is. Previously stamina fell to its floor within about two seconds and had almost no effect on the time.
- Both rules can be switched back to the previous behaviour from the settings drawer ("ルール / Rules"); with both, and the sensor jump guard below, set to the classic option the rules are the original ones. The choice is stored in `localStorage` (`hurdle.rules`) and the personal best is kept per rule set.
- GAME-SUPER-HURDLE default sensor thresholds: acceleration 0.3 G → 1.1 G, jump pitch 0.10 rad → 0.15 rad (both still adjustable from the sensor settings drawer).
- GAME-SUPER-HURDLE sensor jump guard (new default, switchable under "ルール / Rules"): a jump triggered by a sensor only counts when the next hurdle is within one second of flight; keyboard jumps are never filtered. Races recorded with two CORE 3.0 units showed the toe-up trigger firing while the runner stamped to accelerate — off the blocks, after a hit (up to four hops in a row at walking pace) and on the run-in — each costing a full jump with no drive under the new jump rule. Replaying those recordings, the runner reaches the first hurdle about 0.5 s sooner with the guard on. Ignored triggers are counted in the post-race stats and recorded as `jumpIgnored` events. An ignored trigger never costs the real take-off that follows: INSOLE and VS input do not start the 700 ms jump cooldown for it, and in solo with ORPHE CORE, where the sensor script's own cooldown cannot be skipped, the game watches the toe itself until that cooldown has run out.
- GAME-SUPER-HURDLE ranking is kept per rule set (jump × stamina): the ranking screen lists only times run under the rules currently selected and says which. The frozen snapshot and every score saved before the rules became switchable stay on the original-rules board, since the same run is 1–2 s slower under the new defaults. New scores carry a `rules` field; nothing stored is rewritten.
- GAME-SUPER-HURDLE cache busting: `main.js`, `style.css` and every module it imports are requested with one shared `?v=` build id set in `index.html` (the modules through the import map), so a browser can no longer run a stale module next to new ones. `tests/super-hurdle-build-id.test.js` checks the ids match and every local import is mapped.
- GAME-SUPER-HURDLE jump assist (same switch as the guard, shown as "ジャンプ補助 / Jump assist"), from races recorded with first-time elderly players at a care home: (1) a sensor jump that comes too early is held for up to 450 ms and released as the runner enters the take-off zone, instead of coming down on the bar (11 of the 23 jumps that hit); (2) a foot held still through the last 1.5 s of the countdown sets the zero for "toe up", after a VS race in which both CORE units rested at +0.81 / +0.29 rad and 18 hurdles passed without a single jump registering. The CORE sensor script is unchanged: the game hands it a pitch measured from that zero. Replaying the recordings, that race goes from 10 + 9 hits to 5 + 8, and the other VS race from 6 + 4 hits to 1 + 3. Held jumps and the zero are recorded (`jumpHeld`, `pitchZero` events).
- GAME-SUPER-HURDLE take-off cue: the JUMP sign and the take-off zone now start at the earliest take-off that still clears the bar (0.53 s before it, previously 0.47 s); in recorded sensor races a jump prompted on the approach registered a median 0.24 s after the sign. The zone for the following hurdle also stays on the track (unlit) while the runner is airborne: at race pace the runner lands inside it with only about 0.2 s on the ground, too short to react to a sign that appears on landing, which is how every hit in the recorded CORE solo races came about (take-offs drifting later hurdle by hurdle). The coaching comment for late take-offs now says so.
- GAME-SUPER-HURDLE analysis scoring: rhythm uses a robust spread of the hurdle intervals and deducts separately for intervals broken by a hit (one clipped hurdle used to zero the axis), and the finish axis compares the last 30 m with the median mid-race speed (a mid-race hit used to make any finish look strong).
- GAME-SUPER-HURDLE step count: one strike per foot per 350 ms instead of 200 ms. The landing and push-off of one step were often counted twice (29–34 "steps" per foot against 20–25 ground contacts on the INSOLE pressure sensors in the same races).
- GAME-UDON ("うどんふみふみ") is rebuilt (CORE connection via CoreToolkit is unchanged; p5.js is no longer needed). Steps are detected from `gotConvertedAcc` with a gravity-removed envelope instead of the sample-to-sample jump of normalized `gotAcc`: gravity is re-estimated whenever the foot is still, peaks and valleys of the envelope are tracked so that fast continuous stamping is counted as well, and the threshold is selectable in five levels (1.2 G down to 0.1 G) or auto-calibrated, so gentle or seated stepping is counted. If the player keeps moving without a step registering, the sensitivity is raised automatically after a short countdown. Play is kneading → rolling → cutting, and an even stepping rhythm builds a combo that multiplies progress (×1.5 / ×2 / ×3). The result is one of 12 bowls chosen from how the player stepped, with a stepping report (radar chart of rhythm, tempo, left/right balance, power, stamina and steadiness, a step log chart, CSV export, a one-page print layout, a collection and a local history). One CORE is enough to play, and a keyboard/tap demo mode needs none. Played through once on two real COREs; the fast-stamping fix made after that session is verified with synthetic signals only.
- New example GAME-SUPER-PINGPONG (湯けむりピンポン), built from GAME-PINGPONG, which stays as it is: a rehabilitation game for ankle dorsi/plantarflexion (CORE on the instep) and thigh raises (CORE on the thigh). It uses a three.js scene (the game corner of a hot-spring inn with a seasonal garden), procedural Web Audio and ES modules (`main.js`, `game.js`, `input.js`, `analysis.js`, `world.js`, `characters.js`, `fx.js`, `audio.js`, `ui.js`, `report.js`, `store.js`). The CoreToolkit connection block (two COREs, `SENSOR_VALUES`) is the same as in GAME-PINGPONG.
  - Control: the paddle follows a tilt angle measured from the direction of gravity in the sensor frame around an axis found by a three-step range-of-motion calibration, so the sensor can be mounted in any orientation and gyro yaw drift does not move the paddle. No calibration round is needed: the axis and the range in use are learned during play from the last 45 s of gravity samples (plane fit, 4th-96th percentile) and refitted twice a second; the three-step measurement stays available from the settings. Until the player has moved, the angle equals the previous `euler.pitch` control. Sensitivity, smoothing, direction, paddle size and an aim assist are adjustable per player; keyboard and pointer input work without a CORE.
  - Play: versus, co-op rally and solo against a CPU; smashes, three items, an optional landing guide. A rally speeds up with every return, at one of five paces chosen in the settings (off, +4.5%, +8%, +12% or +17% of the starting speed per return, each with a ceiling; the default is +8% up to 2.1×).
  - Characters: each player picks one of six (daruma, maneki-neko, akabeko, tanuki, capybara in a yuzu bath, snow rabbit) from a sheet of portraits rendered from the 3D models; each wears the team colour and has one movement of its own. The table has a net with a visible tape and posts and a painted centre line.
  - Result: each player gets six 0-100 scores (range of motion, activity, smoothness as SPARC, accuracy, reaction, endurance), a total with a rank, a radar chart against the previous session, the tilt over time and one piece of advice; sessions are kept in `localStorage` and can be exported as CSV. A range no joint can do is flagged instead of rated, and the total is scaled by the share of balls returned. An optional raw-data recording saves every sensor sample of a match automatically. These are wellness indicators, not clinical measurements.

### Fixed

- **`lostData()` no longer fires on the uint16 serial wraparound (65535 → 0) and treats serial 0 correctly.** Both header-50 `SENSOR_VALUES` paths (the normal `got*` dispatch path and the `gotData`-override / ORPHE TERMINAL path) compared `this.serial_number - serial_number_prev != 1` and used `if (this.serial_number)` as the "have a previous serial" test, so every wrap reported a bogus `lostData(0, 65535)`, serial 0 was mistaken for "no previous packet", and a real gap across the boundary (e.g. 65535 → 2) went unreported. Gap detection now uses the modular distance `orpheCoreSerialDistance(cur, prev) = (cur - prev + 65536) % 65536` (module scope) with an explicit `_serialInitialized` flag, which is reset by `clear()` / `reset()` and by the disconnect handler so the first packet after a (re)connection never reports. The first packet of a session, header-40 (CORE 2.0) packets and contiguous serials behave exactly as before; a real gap still reports `lostData(cur, prev)` exactly once. Test: `tests/core-serial-gap.test.js`.
- **`setup(names, {})` no longer throws.** `setup()` assigned `options.interpolation` verbatim, so `setup(names, {})` (or any options object without `interpolation`) set `this.interpolation = undefined` and the following `.max_consecutive_missing` access threw a `TypeError`. The option is now merged with the defaults (`{ enabled: false, max_consecutive_missing: 1 }`); `setup()`, `setup(names)`, `setup(names, {})`, `setup(names, null)` and `setup(names, { interpolation: { enabled: true } })` all work and leave `this.interpolation` normalized without mutating the caller's object. Linear interpolation itself is still not implemented — the option is accepted and reserved (documented in the JSDoc and CLAUDE.md). Test: `tests/core-setup-options.test.js`.
- **Overriding `ble.onDisconnect` after `begin()` now takes effect, and `this` inside it is the `Orphe` instance.** Six sites registered `this.onDisconnect` directly with `addEventListener('gattserverdisconnected', …)`, so the listener kept the function that was current at connection time and ran with `this` bound to the `BluetoothDevice`. A single lazily-bound `_onDisconnectHandler` (created once in the constructor) is now registered at all six sites through `_attachDisconnectHandler(device)`, which removes any previous registration of the same handler before adding it, so the callback runs exactly once per event even if the device is (re)attached several times. The auto-reconnect handler (`_autoReconnectDisconnectHandler`) and the BleSharedBridge disconnect hook are untouched. Test: `tests/core-disconnect-handler.test.js`.

## [1.4.1] - 2026-09-05

### Fixed

- **Header 50 (CORE 1.x / 3.0 200 Hz `SENSOR_VALUES`) quaternion is now normalized by its actual norm** instead of being divided by a fixed 32768 (Q15). Real-device raw packets (CORE 3.0, 2026-09-05, 1827 packets) carry a **Q14** quaternion (|q| median 16383, 1.0 = 16384), so the old code halved every component and `gotEuler.yaw` came out at roughly **0.2× the true angle** (a 90° turn read as 15–21°). `gotQuat` now always delivers a unit quaternion regardless of the firmware's fixed-point scale (Q14 or Q15 — which one CORE 1.x uses is unknown, so the fix is scale-agnostic). A zero/degenerate quaternion keeps the previous orientation (identity on the first packet) instead of producing NaN. The header 40 (CORE 2.0) path already used `quatScale = 16384` plus `.normalize()` and is unchanged. Test: `tests/core-quat-normalize-header50.test.js`.
- **Header 50 (CORE 1.x / 3.0 200 Hz `SENSOR_VALUES`) per-sample timestamps are now `t_base − delta_k`** (k = 0, 1, 2 from bytes 28 / 49 / 70), and block 3 — the oldest sample, which has no delta byte (offset 91 is not a delta) — is `t_base − delta_2 − (delta_1 − delta_0)` (= −19 ms with the observed deltas; nominal −20 ms). Real-device raw packets (CORE 3.0, 2026-09-05, 1827 packets) show constant deltas 5 / 10 / 14 ms and consecutive base timestamps advancing 19–20 ms, so the delta is an **age relative to the base timestamp**, and the sample order is block 3 → 2 → 1 → 0 (oldest → newest, established by gyro continuity). The old code added the deltas cumulatively starting from block 3 = `t_base` (0 / +14 / +24 / +29): wrong sign and wrong accumulation, giving intra-packet dt of 14 / 10 / 5 ms and the first sample of the next packet jumping **back by ~9 ms**; integrating gyro against those timestamps inflated angles by ~1.4×. Dispatch order (i = 3 → 0, chronological) and `packet_number = 3 − i` (0 = oldest) are unchanged; the corrected timestamp is applied to `quat` / `gyro` / `acc` / `converted_gyro` / `converted_acc`. Test: `tests/core-header50-sample-timestamps.test.js`. Note: ORPHE-INSOLE.js `parseInsoleSensorValues` (header 50 branch) has the same accumulation pattern and should be checked separately.
- **Accelerometer range index 0 (±2 G) was converted as ±8 G, so `gotConvertedAcc` / `converted_acc` were 4× too large at ±2 G.** Both `SENSOR_VALUES` parse paths (header 50 and header 40) mapped the `device_information.range` index to a full-scale value with an `if` chain without `else` (`if (r == 0) r = 2; if (r == 1) r = 4; if (r == 2) r = 8; …`), so index 0 became 2 and then also matched `== 2` → 8. The gyro chain (250 / 500 / 1000 / 2000) happened not to collide but had the same fragile shape. Both are now lookup tables — `ORPHE_CORE_ACC_RANGE_G = [2, 4, 8, 16]` and `ORPHE_CORE_GYRO_RANGE_DPS = [250, 500, 1000, 2000]` via `orpheCoreRangeIndexToValue(indexOrValue, table)` (module scope). Indexes 1–3 and all gyro results are unchanged; non-index values (e.g. a full-scale value passed directly) still pass through as before. `begin()`'s value → index conversion reads the caller's `range` and writes `obj.range`, so it was not affected and is unchanged. Test: `tests/core-acc-range-mapping.test.js`.

## [1.4.0] - 2026-08-30

### Changed

- **Converted gyro values (`gotConvertedGyro` / `converted_gyro`) now use the per-range LSM6DSOX datasheet sensitivity instead of the ideal Q15 full scale.** Previously `converted_gyro = (raw / 32768) * range`, which corresponds to 61.035 mdps/LSB at ±2000 dps. The sensor's representative sensitivity is 0.035 mdps/LSB per 1 dps of full scale:

  | Gyro range | Sensitivity | deg/s per LSB |
  |---|---|---|
  | ±250 dps | 8.75 mdps/LSB | 0.00875 |
  | ±500 dps | 17.5 mdps/LSB | 0.0175 |
  | ±1000 dps | 35 mdps/LSB | 0.035 |
  | ±2000 dps | 70 mdps/LSB | 0.07 |

  Converted values are therefore **about 14.7% larger than before at ±2000 dps** (new/old ratio 1.14688 = 0.07 / (2000/32768); equivalently, the old formula under-reported by about 12.8%). The same ratio applies at every range for header 50. This mirrors the identical fix shipped in ORPHE-INSOLE.js v1.3.2. Both SENSOR_VALUES packet layouts are covered: header 50 (CORE 1.x, int16 samples) and header 40 (CORE 2.0, int8 samples). For header 40 the int8 payload is treated as the high byte of the int16 raw value (multiplied by 256) before applying the sensitivity, so header 40 and header 50 now yield the same deg/s for the same physical rate (e.g. int8 0x40 and int16 0x4000 both give 1146.88 deg/s at ±2000 dps). Because the old header-40 code normalized by int8/127 rather than by the int16 scale, its change is a slightly different ratio: **1.13792 (about +13.8%)**. The old code's two paths disagreed with each other by about 0.8%; they now agree. The helper `orpheCoreGyroRawToDps(raw, rangeDps)` and the constant `ORPHE_CORE_GYRO_DPS_PER_LSB_PER_RANGE` are exposed at module scope.
- The **normalized gyro callback `gotGyro` (raw / 32768, or int8 / 127 for header 40) is unchanged** for backward compatibility, and the accelerometer conversion (`raw / 32768 * range`, which already matches the datasheet 0.488 mg/LSB at ±16 G) is unchanged.
